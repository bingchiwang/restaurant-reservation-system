# ADR-002: 資料庫交易與桌位預約併發控制機制

## 狀態
已通過 (Accepted)

## 背景 (Context)
在熱門用餐時段，可能有多名顧客在相同毫秒數內送出預約請求。若採用簡單的「查詢可用桌位 → 取得桌號 → 寫入預約」，將發生經典的 Race Condition（競爭條件），導致同一張桌位在重疊時段被重複分配給兩筆訂位。

## 決策 (Decision)

1. **交易邊界 (Transaction Boundary)**：
   - 預約建立與桌位分配必須包裹在資料庫 Transaction（`BEGIN ... COMMIT`）內。
   - 若過程有任何失敗（無合適桌位、預點餐餐點下架、連線異常），立即執行 `ROLLBACK`，不得殘留孤立預約或桌位占用資料。

2. **併發控制方案 (Concurrency Control)**：
   - 採用悲觀鎖 / 排他鎖機制（Pessimistic Locking / `SELECT ... FOR UPDATE`）：
     - 於交易啟動後，依人數篩選候選桌位。
     - 在檢查時段重疊時，對鎖定範圍內的桌位鎖定候選列，防止其他併發交易同時搶占同一桌位。
   - 同時在資料庫約束層面，建立複合唯一約束或在排他驗證通過後立即於 `ReservationTables` 寫入關聯。

3. **時段衝突定義 (Overlapping Interval Rule)**：
   - 給定預約時間區間 \([S_1, E_1)\)（包含預設用餐時長與緩衝時間），與既存有效預約 \([S_2, E_2)\)。
   - 衝突條件：\(\max(S_1, S_2) < \min(E_1, E_2)\)。
   - 排除狀態為 `CANCELLED` 的預約紀錄。

4. **測試環境與資料庫相容性**：
   - 資料庫層支援標準 MySQL，並在 DAO 層統一以參數化介面實作。
   - 單元與整合測試支援輕量級記憶體/檔案資料庫（SQLite WAL mode / In-memory）以確保本機無 MySQL 服務時依然能完整執行自動化測試案例。

## 結果與影響 (Consequences)
- 確保同一桌位於相同時段絕不發生雙重訂位（Double Booking）。
- 嚴格維持資料一致性，並在併發單元測試（如多執行緒發送預約）中被驗證。
